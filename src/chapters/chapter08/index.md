```ql
/**
 * @name AI-generated hardcoded credentials
 * @description Detects credentials that may have been generated by AI
 * @kind problem
 * @problem.severity error
 * @id python/ai-generated-credentials
 */

import python
import semmle.python.dataflow.new.DataFlow

// AI生成コードでよく見られるパターン
from DataFlow::AssignmentCfgNode assign
where
  assign.getVariable().getName().toLowerCase() in 
    ["api_key", "secret_key", "password", "token"] and
  assign.getValue() instanceof DataFlow::LiteralNode and
  // AIがよく生成するプレースホルダーパターン
  assign.getValue().toString().regexpMatch(".*(YOUR_|INSERT_|REPLACE_|TODO|XXX).*")
select assign, "Possible AI-generated placeholder credential detected"
```

### シークレット検出時の対応

#### 即座の対応手順
1. **アラート確認**
   ```bash
   # 該当コミットの特定
   git log --grep="<secret_pattern>"
   ```

2. **シークレットの無効化**
   - 即座にシークレットを無効化
   - 新しいシークレットを生成

3. **履歴からの削除**
   ```bash
   # BFGを使用した履歴クリーニング
   java -jar bfg.jar --delete-files <file_with_secret>
   git reflog expire --expire=now --all
   git gc --prune=now --aggressive
   ```

4. **Force push**（注意が必要）
   ```bash
   git push --force-with-lease
   ```

### Dependency reviewワークフロー

#### PRとmerge queueでの依存関係チェック

```yaml
name: Dependency Review

on:
  pull_request:
  merge_group:
    types: [checks_requested]

permissions:
  contents: read

jobs:
  dependency-review:
    name: Dependency Review
    runs-on: ubuntu-latest
    steps:
      - name: Checkout Repository
        uses: actions/checkout@v4

      - name: Dependency Review
        uses: actions/dependency-review-action@v4
        with:
          fail-on-severity: moderate
          deny-licenses: GPL-3.0, AGPL-3.0
          allow-ghsas: GHSA-xxxx-yyyy-zzzz
```

merge queueは、queue内の変更を組み合わせたtemporary merge group commitに対して`checks_requested`を発行します。
required checkにしたworkflowが`pull_request`だけを購読すると、このcommitに同じcheckが生成されずqueueが停止するため、`merge_group`でも同じ`Dependency Review` checkを実行します。
required status checkの識別にはjob名が使われるため、`Dependency Review`というjob名を固定し、rulesetまたはbranch protectionではGitHubが返す正確なcheck名を選択してください。
required checkにするworkflowへ`paths`または`paths-ignore` filterを設定すると、対象外のPRでworkflowがskipされ、checkがPendingのまま残るため設定しません。
merge queueを使わないrepositoryでは`merge_group` eventが発火しないため、通常のPR検査を妨げません。
全体のrequired check設計は[第13章のmerge queue節](../chapter13/)も参照してください。

公式仕様:

- Merge queue: <https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/configuring-pull-request-merges/managing-a-merge-queue>
- `merge_group` event: <https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#merge_group>
- Required status checksのtroubleshooting: <https://docs.github.com/en/pull-requests/collaborating-with-pull-requests/collaborating-on-repositories-with-code-quality-features/troubleshooting-required-status-checks>

### ライセンスコンプライアンス

#### ライセンスチェックの自動化
```python
# check_licenses.py
import pkg_resources
import json

ALLOWED_LICENSES = [
    'MIT', 'Apache-2.0', 'BSD-3-Clause', 
    'BSD-2-Clause', 'ISC', 'Python-2.0'
]

DENIED_LICENSES = [
    'GPL-3.0', 'AGPL-3.0', 'SSPL'
]

def check_dependencies():
    issues = []
    
    for dist in pkg_resources.working_set:
        license = get_license(dist)
        
        if license in DENIED_LICENSES:
            issues.append({
                'package': dist.project_name,
                'version': dist.version,
                'license': license,
                'severity': 'high'
            })
        elif license not in ALLOWED_LICENSES:
            issues.append({
                'package': dist.project_name,
                'version': dist.version,
                'license': license,
                'severity': 'medium'
            })
    
    return issues
```

## 7.4 AI支援による脆弱性修正提案

### 自動修正の生成

#### Copilotによる修正提案
```python
# 脆弱なコード（CodeQLで検出）
def read_file(filename):
    # CWE-22: Path Traversal
    with open(f"/var/data/{filename}", 'r') as f:
        return f.read()

# Copilot提案の修正
def read_file(filename):
    # Validate filename to prevent path traversal
    if '..' in filename or filename.startswith('/'):
        raise ValueError("Invalid filename")
    
    # Use pathlib for safe path construction
    from pathlib import Path
    safe_path = Path("/var/data") / filename
    
    # Ensure the resolved path is within allowed directory
    if not safe_path.resolve().is_relative_to("/var/data"):
        raise ValueError("Access denied")
        
    with open(safe_path, 'r') as f:
        return f.read()
```

### セキュリティパッチの自動生成

#### 実行可能なCodeQL scanワークフロー

次の例は、buildが不要なJavaScript / TypeScriptを対象にCodeQL databaseを準備し、SARIFをcode scanningへ送るadvanced setupです。
AI/Autofixによる修正やPull Request作成までは行いません。

{% raw %}
```yaml
name: CodeQL

on:
  push:
    branches: [main]
  pull_request:
    branches: [main]
  schedule:
    - cron: '0 0 * * 0'

permissions:
  contents: read
  security-events: write

jobs:
  analyze:
    runs-on: ubuntu-latest
    steps:
      - name: Checkout scan target
        uses: actions/checkout@v4

      - name: Initialize CodeQL database
        uses: github/codeql-action/init@v4
        with:
          languages: javascript-typescript
          build-mode: none

      - name: Analyze and upload SARIF
        uses: github/codeql-action/analyze@v4
        with:
          category: /language:javascript-typescript
```
{% endraw %}

実行順序は`checkout → init → languageに応じたbuild → analyze`です。
JavaScript / TypeScriptではbuildは不要なので、`init`で`build-mode: none`を明示し、`autobuild` stepを置きません。
一方、build情報が必要なcompiled languageでは、現行の公式guidanceに従って`init`へ`build-mode: autobuild`を指定するか、`build-mode: manual`を指定して`init`と`analyze`の間で再現可能なbuild commandを実行します。
対象languageのbuild要否と利用できるbuild modeは公式文書で確認し、不要なbuildを一律に挿入しないでください。

この例の`@v4`は教材上のmajor tagです。本番workflowでは組織のsupply-chain方針に従い、actionを監査済みcommit SHAへ固定し、更新時にrelease noteと権限差分を再確認します。

このjobでcheckoutするfork由来のuntrustedなPR codeは、信頼済み入力ではなくscan対象です。
`security-events: write`は解析結果をcode scanningへ送るために限定し、`contents: write`、`pull-requests: write`、repository secretsは与えません。
untrustedなPR codeを解析するjobと、修正のcommitやPull Requestを作るprivileged jobを同じjobで実行しないでください。

公式の実行契約は次の文書で確認します。

- Code scanning workflow options: <https://docs.github.com/en/code-security/reference/code-scanning/workflow-configuration-options>
- Preparing code for analysis: <https://docs.github.com/en/code-security/tutorials/customize-code-scanning/prepare-code-for-analysis>

#### AI/Autofixは分析後の別工程

`analyze`後にcode scanning alertが生成されてから、対応環境でAI/Autofixの修正提案を検討します。
修正提案はuntrustedなPR codeやSARIFを自動的に信頼済みへ昇格させるものではありません。
差分、テスト、権限変更、依存更新を人間レビューし、通常のbranch protectionとCIを通してmergeします。
write自動化が必要な場合も、scan結果を検証するtrustedな後段へ分離し、PR codeや未検証artifactをprivileged contextで実行しません。

## 7.5 セキュリティアラートの管理

### アラートのトリアージ

#### 優先順位付けマトリックス
```python
class SecurityTriage:
    def __init__(self):
        self.severity_scores = {
            'critical': 10,
            'high': 7,
            'medium': 4,
            'low': 1
        }
        
        self.exploitability_scores = {
            'publicly_exploited': 10,
            'poc_available': 7,
            'theoretical': 3
        }
        
    def calculate_priority(self, alert):
        base_score = self.severity_scores[alert.severity]
        exploit_score = self.exploitability_scores[alert.exploitability]
        
        # ビジネスクリティカルなコンポーネントか
        if alert.component in CRITICAL_COMPONENTS:
            business_impact = 10
        else:
            business_impact = 5
            
        # 外部公開されているか
        exposure = 10 if alert.is_external else 3
        
        priority = (base_score * 0.3 + 
                   exploit_score * 0.3 + 
                   business_impact * 0.2 + 
                   exposure * 0.2)
                   
        return round(priority, 1)
```
